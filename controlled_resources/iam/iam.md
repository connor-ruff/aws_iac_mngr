# IAM Module

This module manages the manually-created IAM roles in Connor's AWS account. These roles were originally created through the AWS Console and are being imported into OpenTofu so they're visible and managed as code going forward.

## File structure

Each IAM entity (a role plus its policies and attachments) lives in its own `.tf` file named after the thing it represents. Everything you need to understand a role's permissions is in one place — no jumping between files.

| File | What it manages |
|---|---|
| `main.tf` | Backend (S3 remote state), AWS provider, and shared `locals` |
| `eventbridge_scheduler_gdrive_snowflake.tf` | EventBridge Scheduler role that triggers `lambda-gdrive-to-snowflake-pipe` |
| `eventbridge_scheduler_zeta_ball.tf` | EventBridge Scheduler role that triggers `lambda-zeta-ball-api-to-sf` |
| `lambda_convert_excel_to_csv.tf` | Lambda role for the Excel → CSV converter |
| `lambda_ebird.tf` | Lambda role for eBird API data pulls |
| `lambda_gdrive_to_snowflake.tf` | Lambda role for the Google Drive → Snowflake pipeline |
| `lambda_zeta_ball.tf` | Lambda role for the Zeta Ball API → Snowflake pipeline |
| `rds_monitoring.tf` | RDS enhanced monitoring role |
| `snowflake_external_function.tf` | Role that allows Snowflake to call API Gateway endpoints |
| `snowflake_s3_integration.tf` | Role that allows Snowflake to read from S3 |

## How an entity file is structured

Each entity file follows the same pattern: role → policy → attachment → import blocks. Here's `lambda_zeta_ball.tf` as a walkthrough:

```hcl
resource "aws_iam_role" "lambda_zeta_ball_api_to_sf" {
  name = "lambda-zeta-ball-api-to-sf-role-065dfwgs"
  path = "/service-role/"
  ...
}
```

The **role** is the identity. Its `assume_role_policy` (the trust policy) controls *who is allowed to assume this role* — in this case, `lambda.amazonaws.com`, meaning only Lambda functions can use it.

```hcl
resource "aws_iam_policy" "lambda_basic_execution_zeta_ball" {
  name = "AWSLambdaBasicExecutionRole-3d5f6f34-..."
  ...
  policy = jsonencode({ ... })
}
```

The **policy** defines *what the role is allowed to do* once assumed. This one grants CloudWatch Logs write access (so the Lambda can emit logs), Secrets Manager read access for the Yahoo Fantasy API keys, and S3 write access to the `zeta_ball/` prefix.

```hcl
resource "aws_iam_role_policy_attachment" "lambda_zeta_ball_execution" {
  role       = aws_iam_role.lambda_zeta_ball_api_to_sf.name
  policy_arn = aws_iam_policy.lambda_basic_execution_zeta_ball.arn
}
```

The **attachment** binds the policy to the role. Without this, the policy exists in AWS but isn't actually applied to anything.

```hcl
import {
  to = aws_iam_role.lambda_zeta_ball_api_to_sf
  id = "lambda-zeta-ball-api-to-sf-role-065dfwgs"
}
# ... one import block per resource
```

The **import blocks** tell OpenTofu to adopt the existing AWS resources into state rather than creating new ones. These only matter the first time `tofu apply` is run against a resource — after that they're inert but harmless to leave in place.

## Snowflake trust relationships

Two roles (`snowflake_s3_integration.tf` and `snowflake_external_function.tf`) trust Snowflake's AWS IAM user (`arn:aws:iam::735350675005:user/4cw40000-s`) as their principal instead of an AWS service. The `sts:ExternalId` values in those trust policies are generated by Snowflake and prevent the [confused deputy problem](https://docs.aws.amazon.com/IAM/latest/UserGuide/confused-deputy.html). **Do not change these external IDs** — they're tied to the Snowflake integration config and changing them would break the integrations.

`snowflake_external_function.tf` has two statements in its trust policy because the role is used by two separate Snowflake external functions, each with a different external ID.

## How to apply

These resources already exist in AWS. The `import` blocks tell OpenTofu to adopt them into state rather than creating new ones.

```bash
cd iam/
tofu init
tofu plan   # should show only imports, no creates or destroys
tofu apply  # executes the imports
```

If `tofu plan` shows resource modifications (not just imports), the `.tf` definition doesn't exactly match what's in AWS. Review the diff and update the file before applying.
