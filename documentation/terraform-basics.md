# Terraform Basics

## How Terraform works

Terraform reads all `.tf` files in a directory and treats them as a single combined configuration. The filename doesn't matter — Terraform merges everything together before doing anything. The convention of splitting things across `main.tf`, `variables.tf`, `outputs.tf`, etc. is just organization, not a requirement.

When you run a `tofu` command from inside a directory, that directory is the **root module** — the scope of what Terraform is aware of and managing.

## Core file types

### `main.tf`
By convention, where the primary resource definitions live. There's nothing special about the name — it's just where most people put the bulk of their config.

### `variables.tf`
Defines input variables — values you want to parameterize rather than hardcode. Not used in bootstrap (everything is fixed), but common in larger modules.

### `outputs.tf`
Defines values that Terraform prints after `apply` completes. Also allows other modules to reference values from this module.

### `terraform.tfvars`
Where you supply values for variables. Never commit this file if it contains secrets.

### `terraform.tfstate`
Auto-generated by Terraform. Tracks everything it has created. Never edit this manually. When using a remote backend (S3), this file lives in the cloud instead of locally.

## The three block types you'll see everywhere

### `terraform {}`
Top-level configuration for Terraform itself. Used to declare which providers are required and which version of them to use. Also where you configure the backend (where state is stored).

```hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}
```

### `provider {}`
Configures a provider — in this case AWS. This is where you tell Terraform which region and credentials to use. A provider is essentially a plugin that knows how to talk to a specific cloud or service.

```hcl
provider "aws" {
  region  = "us-east-2"
  profile = "connor-ruff-dev-acct"
}
```

### `resource {}`
The most common block. Declares a piece of infrastructure you want to exist. Takes two labels: the resource type (defined by the provider) and a local name you choose.

```hcl
resource "aws_s3_bucket" "my_bucket" {
  bucket = "my-bucket-name"
}
```

The local name (`my_bucket`) is how you reference this resource elsewhere in your config. It has no effect on what gets created in AWS.

## References between resources

Resources can reference each other using the pattern `<type>.<local_name>.<attribute>`. Terraform uses these references to automatically figure out the order things need to be created in.

```hcl
resource "aws_s3_bucket_versioning" "example" {
  bucket = aws_s3_bucket.my_bucket.id  # references the bucket created above
}
```

## The core commands

| Command | What it does |
|---|---|
| `tofu init` | Downloads the required providers. Run once per module, or after changing provider versions. |
| `tofu plan` | Compares your `.tf` files against current state and shows what would be created, changed, or destroyed. Nothing is actually done. |
| `tofu apply` | Runs the plan and, after confirmation, makes the changes in AWS. |
| `tofu destroy` | Destroys everything in the current module's state. Use with care. |
| `tofu output` | Prints the values defined in `outputs.tf` after a successful apply. |

## What happens when you run `tofu apply`

1. Terraform reads all `.tf` files in the directory
2. It loads the current state (from local file or remote backend)
3. It calls the AWS API to check the real current state of resources
4. It computes a diff: what needs to be created, updated, or deleted
5. It shows you the plan and asks for confirmation
6. It makes the changes and updates state

## Walkthrough: the bootstrap module

Here's exactly what happens when you run `tofu apply` inside `bootstrap/`.

### Step 1 — `terraform {}` block (`main.tf` lines 1–8)

```hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}
```

Declares that this module needs the AWS provider at version 5.x. `tofu init` uses this to download the right plugin. The `~> 5.0` means "5.0 or higher, but not 6.0" — allows patch updates but not breaking major version changes.

### Step 2 — `provider {}` block (`main.tf` lines 10–13)

```hcl
provider "aws" {
  region  = "us-east-2"
  profile = "connor-ruff-dev-acct"
}
```

Configures the AWS provider. All resources in this module will be created in `us-east-2` using your SSO profile. Terraform uses the same credential chain as the AWS CLI, so as long as you've run `aws sso login --profile connor-ruff-dev-acct`, this just works.

### Step 3 — The S3 bucket (`main.tf` lines 15–17)

```hcl
resource "aws_s3_bucket" "terraform_state" {
  bucket = "connor-ruff-terraform-state"
}
```

Creates the bucket. The local name `terraform_state` is used in the next three blocks to reference this bucket — Terraform knows to create the bucket first before configuring it.

### Step 4 — Versioning, encryption, public access (`main.tf` lines 19–44)

These three resources are all configuration applied to the same bucket. Notice they all reference `aws_s3_bucket.terraform_state.id` — Terraform automatically resolves this reference, so it knows these three resources depend on the bucket and must be created after it.

```hcl
resource "aws_s3_bucket_versioning" "terraform_state" {
  bucket = aws_s3_bucket.terraform_state.id  # reference to the bucket above
  ...
}
```

In older versions of the AWS provider, all of this was done inside the `aws_s3_bucket` block. The provider now requires them as separate resources — more verbose, but each concern is isolated.

### Step 5 — DynamoDB table (`main.tf` lines 46–55)

```hcl
resource "aws_dynamodb_table" "terraform_state_lock" {
  name         = "terraform-state-lock"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "LockID"

  attribute {
    name = "LockID"
    type = "S"
  }
}
```

Creates the lock table. This resource has no reference to the S3 bucket, so Terraform may create it in parallel with the bucket — the order between these two doesn't matter.

### Step 6 — Outputs (`outputs.tf`)

```hcl
output "state_bucket_name" {
  value = aws_s3_bucket.terraform_state.bucket
}

output "state_lock_table_name" {
  value = aws_dynamodb_table.terraform_state_lock.name
}
```

After `apply` completes, Terraform prints these values to the terminal. Useful for confirming what was created and for copying values you'll need when configuring backends in other modules.
